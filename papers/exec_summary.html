Executive Summary — June 2026

Tensor Logic & Neural Circuit Diagrams

A system in which mathematical equations are the implementation — compiling directly to executable PyTorch modules and formally verified Lean 4 specifications, with no hand-written translation between them.

1

The Problem Solved

Modern deep learning research is bottlenecked by a translation gap. A researcher writes a model in clean mathematical notation — a few equations over named indices, then translates it by hand into hundreds of lines of PyTorch, where the mathematical structure is invisible. Bugs hide in that translation. Architectural variants require rewriting large swaths of imperative code. Formal reasoning about the model is impossible.

We close that gap. You write the model in mathematical notation; the system compiles it directly to a correct, runnable nn.Module. The same notation also compiles to a formal proof assistant (Lean 4), enabling rigorous mathematical claims about the architecture.

Core principle: Contraction structure is read from axis identity, not from an explicit specification. An axis that appears on both sides of an equation is retained; one that appears only on the right is summed over. No einsum strings, no shape manipulation — just equations.

2

What It Looks Like

The system is built on tensor logic, a mathematical formalism for machine learning in which every computation (whether a neural forward pass, a probabilistic inference query, or a logical deduction) is a tensor contraction over named axes. Key advantages make it a natural foundation:

  • Universality. Neural networks, probabilistic graphical models, and logic programs are all special cases; tensor logic subsumes the three historically separate paradigms of ML under one formalism.
  • Gradient learnability. Every tensor logic expression is differentiable; gradient descent applies uniformly across all model families, not just to neural architectures.
  • Neurosymbolic integration. First-order logical relationships (quantification, relations, predicates) translate directly into tensor expressions, making relational structure a first-class citizen alongside numerical computation. Symbolic reasoning and neural computation are not separate systems requiring a bridge, but different aspects of a common framework; a model can simultaneously learn continuous representations (embeddings) and enforce discrete logical constraints within a single unified computation.
  • Compositionality. Complex models are assembled by composing simpler tensor expressions; the compositional structure is explicit and carries through to interpretation and analysis. Tensor logic naturally permits predicate invention: new relational concepts can be introduced as learned tensor predicates and composed into existing models, enabling the system to discover and name intermediate abstractions rather than hand-engineering them.
  • Hardware affinity. Tensor contractions map directly to GPU/TPU accelerators. The formalism is both mathematically principled and computationally practical on the same hardware that runs production models.

All examples below are written in the Lean 4 DSL. The same specification compiles identically from the Python DSL, and every example has a direct translation to PyRel (more on that below).

Causal self-attention

Scaled-dot-product attention with a causal mask, the central operation in every modern transformer:

tensor Q(q, h, k), K(x, h, k)
predicate causal(q, x)           -- Bool mask: 1 where x ≤ q, 0 elsewhere
Attn[h, q, x.] := softmax(Q[q, h, k] · K[x, h, k] · causal[q, x])

The compiler infers: k is absent from the output → sum over it (the dot product). causal is Bool-typed → it gates the sum to valid positions. x. marks the key-position axis as the softmax normalization dimension. No imperative code is written.

Two-layer MLP

linear W_in(f, d), W_out(d, f)             -- learned weights; roles inferred from equations
H[q, f]   := relu(W_in[f, d] · X[q, d])    -- d contracted → hidden layer
Out[q, d] := W_out[d, f] · H[q, f]         -- f contracted → output projection

Three lines compile to a two-layer module with learned weights, a ReLU activation folded into the first layer, and automatic threading of the intermediate tensor H. The linear keyword is the only signal needed to make a weight trainable; axis roles are read from the equations.

PyRel translation. Every tensor-logic program has a mechanical translation to PyRel (Relational AI's Datalog extension), where tensors become relations and contraction becomes sum(product).per(output_indices). The MLP above becomes two where(…).define(…) rules, one per equation, that can be evaluated, queried, and composed like any other relational program. This translation is documented and tested for all worked examples.

Deep MLP with recurrence

axis l : ℕ = 3                                               -- scan depth; l runs 0..2
linear W_in(dh, d0), W_out(c, dh), W(l, dh_in, dh)
h[q, dh, 0]    := W_in[dh, d0] · x[q, d0]                    -- base case
h[q, dh, l +1] := relu(W[l, dh_in, dh] · h[q, dh_in, l])     -- recurrence step
y[q, c.]       := softmax(W_out[c, dh] · h[q, dh, 3])        -- output projection

The compiler detects the scan from the l +1 / l pattern, constructs a scan module, and, when the recurrence is affine in the state, automatically lowers it to a parallel prefix scan for GPU efficiency. Reading a fixed step (h[q, dh, 3]) is validated at build time.

2D Convolution + strided pooling

tensor Filter(dx, dy, ch), Image(xi, yi, ch), Features(x, y)
Features[x, y] := relu(Filter[dx, dy, ch] · Image[x + dx, y + dy, ch])
Pooled[xo, yo] := Features[2 * xo + px, 2 * yo + py]

The affine index expressions x + dx, y + dy, 2 * xo + px compile to reindexing morphisms ("St morphisms") composed around the einsum core. Gather bounds are validated at build time, eliminating runtime out-of-range errors.

Every tensor-logic program moves through a three-stage pipeline. Each stage is a mathematically precise transformation (on categories), which is what makes the system correct by construction rather than by convention.

C♯ — the schema defines the structure of the computation: which axes (dimensions) exist, which tensors they belong to, which axes are contracted versus broadcast, and in what order operators compose. Think of it as a database schema: no sizes, no weights, no numerical content — just the shape of the computation.

∫D — the populated instance is that schema with data filled in: axis sizes, coefficient tensors, and learnable weight parameters. Continuing the database analogy, this is the schema with its rows populated — a fully concrete, queryable object. Every field the schema declared is now assigned a value.

construct() maps this mathematical object to a runnable nn.Module. It is a functor in the categorical sense: it preserves the compositional structure, so a model built from correct pieces compiles to a correct whole. No part of the pipeline is ad-hoc.

One specification compiles to four backends with no additional translation — changing backends changes only the target of construct(); the two stages before it are identical:

The categorical structure guarantees semantic equivalence across backends — a proposition proven about the Lean representation holds for the PyTorch compiled module by construction of the compilation functor.

A Lean 4 implementation

A parallel implementation in Lean 4. The DSL is parsed by the Lean elaborator (as a tlprog!{} macro), type-checked, and evaluated on concrete Float tensors. This is not a simulation or a port — it is a native Lean development with its own structural pipeline, UID system, and evaluator. Crucially, the mathematics underlying the system is directly represented and proved within Lean itself: the categorical structures are Lean types, and the correctness properties are Lean theorems. All #guard tests pass; lake build Tests is green.

Lean ↔ Python interop. The two implementations share a common ground through a serialized relational representation of the data defining the graded colored PROP — the ∫D instance described in the pipeline above. The structural objects (axis declarations, morphism trees, UID maps, etc) are expressed as typed relational tables that both Lean and Python can read and write. This means a model specified in one language can have its compiled structure inspected, extended, or verified in the other.

A clean, unified declaration API

Learnable weight declarations are syntactically identical to ordinary tensor declarations — a flat axis list, nothing more:

linear W_Q(h, k, d)            -- same form as: tensor Q(q, h, k)
linear W_in(f, d), W_out(d, f) -- multiple weights in one declaration

Which axes are contracted (shared with the activation) vs. produced (shared with the output) is fully determined by the equation, not the declaration. The compiler infers both roles and validates them — an axis that is ambiguous or floating raises a precise error at build time.

A mathematical foundation

The system is grounded in a new D-graded colored PROP framework — a mathematical structure that spans the full stack, from high-level ml programmer intent (equations over named axes) through the structural algebra of tensor contractions, down to low-level GPU execution patterns (parallel prefix scans, fused reindexing, scatter/gather). Each level of that stack is a formal object in the framework, and transitions between levels are structure-preserving maps whose correctness is provable. The key ideas:

Mathematical conceptWhat it means in practice
Tensors are wires (objects)A tensor such as Attn[h, q, k] is a wire typed by its axes — it is an object in the PROP, not yet a computation. The wire is not atomic: it is the combination of an output-data object (the tensor's storage type) and a monoidal product h ⊗ q ⊗ k of axis objects, each of which carries its own morphisms (indexing arithmetic — strides, offsets, reorderings).
Equations are morphismsMorphisms are the computations — an equation like Y[i,j] = W[i,k] * X[k,j] maps one group of typed wires to another. The full DSL program is a composition of such morphisms. Computations themselves have internal structure: capability mixins (scan laws, symmetries, attention patterns) attach parametrically to the morphism layer, so a model inherits new behaviour without changes to its equations.
Contraction is compositionThe shared axis k is a categorical boundary being composed over — not an index to be summed by hand. Contraction is correct by construction.
Weaves are cartesian liftsBroadcasting over batch dimensions is not special-cased — it is the cartesian-lift datum of a grading fibration, generalizing to any affine reindexing.
Compilation is a functorconstruct() preserves composition and tensor product — a composed model is correct if and only if its pieces are correct.
Diagrammatic representationString diagrams are a graphical calculus for the PROP — morphisms compose by connecting wires, contraction is a loop, broadcasting is a crossing. They provide a visual, unambiguous representation of code.

A significant property of this foundation is its modularity. The framework is a layered tower: a lightweight categorical base, a parametric core, and composable capability mixins. New capabilities attach as new mixin layers without touching the proven core; new execution targets are new typeclass instances. Correctness theorems proven at the core level are inherited automatically by every extension.

Longer-term

GPU query optimization

The structural representation of a compiled model (a morphism in the PROP) is a query plan as much as an execution plan. Because contraction order, fusion opportunities, and reindexing steps are explicit in the morphism tree, an optimizer can rewrite them (e.g. fuse adjacent reindexings, reorder contractions for memory locality) without touching the source equations. The mathematical foundation guarantees that any rewrite preserving the morphism's semantics is correct.

Performance
Longer-term

Horizontal and vertical extensions

The categorical foundation is designed to grow in two directions. Horizontally, new capability mixins extend what morphisms can express: SymmetryGraded (permutation equivariance for graph and set models) and ensemble methods (model-level vertical extension where entire architectures become first-class objects) are the likeliest first candidates — both reuse proven categorical laws by parametricity rather than requiring new proofs. Vertically, lifting the grading from operation level to model level makes meta-operations like layer stacking and architecture search first-class morphisms with the same correctness guarantees.

Parametric extensibility
Longer-term

Automatic differentiability

Because every compiled model is a morphism in a PROP with a known algebraic structure, automatic differentiation (backpropagation) can be derived as a functor rather than implemented imperatively. The chain rule becomes the compositional law of the PROP; each primitive operation contributes its derivative morphism. This would replace the current dependence on PyTorch's autograd with a provably correct, framework-independent differentiation pass derived directly from the mathematical foundation.

Framework independence

The compounding value

Each layer of the system amplifies the ones below it. An equation-level change — say, adding a relative positional bias — propagates automatically to all backends. A correctness proof about a base operation covers every architecture that uses it. A new execution backend (quantized inference, a hardware simulator) requires only a new algebra instance in the categorical framework, not a new compiler.
